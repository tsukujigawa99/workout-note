1. 目的と前提

項目内容

3. 画面設計（画面遷移と URL）

  • 不正な URL（存在しない画面、壊れた日付、2000-01-01〜今日+1年の範囲外）はホームまたは今日に直し、URL も書き換えます。旧形式 #/entry/<種目ID> は今日として解釈します。
  • マスタに無い種目ID でも、その日に記録があれば「（不明な種目）」として開いて削除できます。
  • タブ同士の切替、種目選択→セット入力は履歴を置き換えます（戻るでホームへ出る）。
  • PC幅（960px以上）は 920px の中央カラム。記録カードは複数列、履歴カードは2列。

4. データ設計

4.1 同期するデータ（Firestore と localStorage で同じ形）

days     : { "YYYY-MM-DD": { memo, items: [ { ex: 種目ID, sets: [ { w: number|null, r: number|null, memo, assist: boolean } ] } ], updatedAt } }
body     : { "YYYY-MM-DD": { w?: 体重kg, f?: 体脂肪率%, updatedAt } }
master   : { parts: [ { id, name, color, hidden? } ], exercises: [ { id, part, name, hidden? } ], updatedAt }   // 配列の順＝表示順
settings : { step: 2.5, timerSec: 90, updatedAt }
データFirestore のパスlocalStorage のキー（未ログイン時）
日々の記録users/{uid}/days/{YYYY-MM-DD}won-days
体組成users/{uid}/body/{YYYY-MM-DD}won-body
部位・種目users/{uid}/meta/masterwon-master
設定users/{uid}/meta/settingswon-settings
  • 種目ID は不変。名称を変えても過去の記録がつながります。新規ID は時刻＋乱数＋連番で衝突を避けます。
  • 種目・部位の削除は hidden: true。過去の記録と履歴には名前を出し続け、種目選択にだけ出しません。
  • 空になった日（種目なし・メモなし）と空の体組成は、ドキュメントごと削除します。
  • 名称は前後の空白を除いて40文字まで。同じ部位内の同名種目、同名の部位は登録できません。
  • 日付キーは端末のローカル時刻で作ります（toISOString は UTC になり日付がずれるため使いません）。
  • Firestore には undefined を渡しません（未入力の項目は省く）。

5. 計算ルール

項目ルール
有効セット回数 r > 0 のセット。重量が空なら 0kg 扱い。
推定1RMw × (1 + r / 40)。小数2桁（履歴カードの MAX は1桁）。検算値：35×15→48.13、35×20→52.50、58×33→105.85（参考にした市販アプリの表示と一致）。
ボリュームΣ(w × r)。トン表示は kg ÷ 1000 を小数2桁。
7日間・28日間今日を含む直近7日／28日。週別バーは今日起点で7日ずつ6本（今週、1〜5週前）。
乗り物換算乗用車 1,500kg、バス 15,000kg、旅客機 350,000kg。小数1桁。
実施日数有効セットが1つ以上ある日を数える。MONTHLY ARCHIVE は表示中の月、TOTAL は全期間。
RM計算機の目安目安重量 ＝ 1RM ÷ (1 + 回数 / 40)。回数は 3, 5, 8, 10, 12, 15。
グラフの目盛り実データの最小・中間・最大を表示（範囲外の数値を出さない）。
「今日」描画のたびに取得し、日付をまたいだら追従。

計算は calc.js に純粋関数として集め、画面や保存先に依存させていません。自動テストの主な対象です。

7. 保存の窓口 store の仕様

画面は store だけを使います。読みは同期（メモリ上の一覧から即座に返す）、書きは非同期です。保存先の違いはアダプタが吸収します。

await store.init()                 // 保存先から読み込み、メモリに展開
store.onChange(cb)                 // データが変わった時（他端末・他タブの変更を含む）に再描画
store.days()  / store.day(k)       / store.saveDay(k, day)    // 種目もメモも空なら削除
store.bodies()/ store.body(k)      / store.saveBody(k, rec) / store.patchBody(k, 変更した項目だけ)
store.master()/ store.saveMaster(m)
store.settings()/ store.saveSettings(s)
store.useAdapter(next)             // 保存先の切替（切替中は全書き込みを拒否）
store.syncState() / store.onSync(cb) / store.onError(cb) / store.onNotice(cb)
アダプタ使う場面保存先特記事項
LocalAdapter未ログインlocalStorage（JSON）読めないデータは退避してから通知。他タブの変更は storage イベントで再読込。書き込み失敗（容量など）は通知。
FirebaseAdapterログイン中Firestore（IndexedDB の永続キャッシュ付き。使えなければメモリ）4つの購読（days, body, meta/master, meta/settings）。書き込みは完了を待たない（オフラインでは完了しないため）。

saveDay は「窓口が持つ最新の1日分に、手元の種目だけを差し替えて」書きます。他端末が同じ日の別種目を足していても消しません。体組成は変更した項目だけを送ります。

8. 同期設計（クラウドを壊さないための決まり）

設計原則は「クラウドの記録を絶対に壊さない」です。テストで見つかった上書き事故の経路を、次の決まりで塞いでいます。

決まり内容防いでいる事故
一覧は毎回作り直すスナップショットが届くたび、差分ではなく全体からメモリ上の一覧を作り直す。直前と内容が同じなら再描画しない。移行の一括書き込みや別タブの書き込みが一覧に入らず、その日に入力すると上書きになる。
ready まで保存しないコレクションごとに ready フラグを持ち、未 ready の間は保存を拒否して通知する。読み込みが遅い時に「空」を前提に保存し、クラウドの種目を消す。
信頼できるスナップショットだけを ready とみなすサーバー由来は信頼。キャッシュ由来は、この端末がその uid で同期した実績（won-synced）があり、かつ前回は中身があったのに今回が空、という形でない時だけ信頼。初回ログイン直後の「キャッシュ由来の空」を正として上書きする。
切替中は入力を止める保存先の切替（ログイン・ログアウト・ユーザー切替）中は全画面の読み込み表示。完了時は入力中の下書きを捨てて現在の画面を作り直す。端末内の内容を元にした下書きがクラウドへ書かれる。
遅れて届いた最初のスナップショットも必ず反映読み込みのタイムアウト後に届いても通知し、画面ごと作り直す。クラウドの記録が画面に出ないまま使い続ける。
自分の入力中は画面を作り直さないセット入力中に他端末の変更が届いた場合、手元で未変更なら最新で作り直し（フォーカス復元）、変更済みなら手元を優先。他の画面は入力が終わってから反映。入力中にフォーカスやキーボードが飛ぶ。
エラーからの自動復帰購読エラー時は 5秒→15秒→60秒間隔で再購読。オンライン復帰・画面復帰・設定の「再接続」でも再試行。ルール適用後もアプリを開き直すまで同期が戻らない。

端末内記録の移行

  • ログイン後、サーバーに直接問い合わせてクラウドの中身を確認してから判断します（オフラインなら次回に持ち越し）。
  • クラウドが空で端末内に記録あり → 確認のうえ全件アップロード。クラウドにも記録あり → クラウドに無い日付だけ追加（上書きしない）。実行直前にもう一度サーバーを確認します。
  • 部位・種目はクラウド優先。ただし端末内にしか無いものは ID で追加します（移行した記録が「不明な種目」にならないように）。
  • 書き込みは 500 件ごとの一括（writeBatch）。端末内の元データは消さずに残します。辞退しても、設定の「端末内の記録をクラウドへ追加」からやり直せます。

9. 認証設計

  • Google ログインは signInWithPopup。signInWithRedirect は、認証用ドメイン（firebaseapp.com）とアプリのドメイン（github.io）が別のため、Safari の制限で失敗するので使いません。
  • ポップアップはタップの直後に同期的に開きます（間に待ちを挟むとブロックされるため）。そのため SDK は起動時に先読みし、読み込み前に押された場合は「準備中」と知らせます。
  • 処理中の連打は無視（120秒で自動解除）。キャンセル・ブロック・ネットワーク・未承認ドメインは日本語で出し分けます。
  • ログイン状態は SDK が端末に保持します。ログイン済みならオフラインでも起動できます。
  • ログインは任意です。全画面のログイン壁にはせず、ホームの案内カード（「あとで」で非表示）と設定画面から行います。
  • アクセス制御は Firestore のセキュリティルール（request.auth.uid == uid）で行います。firebaseConfig は公開前提の値です。
未確定事項：iPhone のホーム画面アプリでのログインiOS のバージョンによっては、ホーム画面アプリから開いたポップアップが呼び出し元に戻れず失敗する事例があります。実機で失敗した場合の代替案は、Google の OAuth で ID トークンをリダイレクトで受け取り signInWithCredential に渡す方式（ポップアップ不要。Google Cloud 側でリダイレクト先の登録が必要）です。

10. PWA・オフライン設計

キャッシュ名中身方針
won-shell-<版>アプリシェル（index.html、CSS、全 JS、アイコン、manifest）インストール時に取得。応答はキャッシュを先に返し、裏で更新（stale-while-revalidate）。版が変わると古いものを削除。
won-sdk-<SDK版>Firebase SDK の3ファイル（app / auth / firestore）版が URL に入った不変ファイルなのでキャッシュ優先。取得に失敗しても Service Worker のインストールは成功させる。
won-fonts-…Google Fonts実行時にキャッシュ。取れなくても代替フォントで表示。
  • Firestore・ログイン関連の通信（firestore.googleapis.com、identitytoolkit、securetoken、apis.google.com、firebaseapp.com）には Service Worker は一切手を出しません。
  • 登録は localhost か HTTPS の時だけ、1回だけ行います。
  • リリース時は sw.js の CACHE_VERSION と defaults.js の APP_VERSION を必ず上げます。SDK の版を変える時は firebase-config.js と sw.js の両方（テストが一致を検査）。
  • SDK が読めない時（初回オフラインなど）もアプリは端末内保存で起動し、通知します。
  • iPhone のノッチ周りは viewport-fit=cover と env(safe-area-inset-*) で処理しています。

11. 操作の安全設計と入力ルール

項目設計
自動保存入力のたびに保存。保存ボタンなし。入力中は画面を作り直さず、該当箇所だけ更新する（フォーカスとキーボードを保つ）。
空セットの扱い画面上は空の3セットを見せるが、保存するのは有効セットだけ。
数値の丸め重量 0〜999.5kg（小数2桁まで）、回数 0〜999 の整数、体重 0〜999.9、体脂肪 0〜100。負数・非数は未入力扱い。
±ボタン重量の刻みは設定値。空で＋なら「前セット→前回の1セット目→20kg」、回数は10から。
取り消しと確認値のあるセットの削除は「元に戻す」付き通知（約5秒、直前の1件）。前回コピーは入力済みなら確認。種目記録の削除とログアウトは確認。
誤タップ防止ボタン付き通知は消えた後も約0.6秒その場でタップを吸収（下のボタンへの抜け防止）。戻る操作の後0.45秒、画面遷移の後0.3秒はボタン操作を無視（ダブルタップで2画面戻る事故の防止）。
表示の安全利用者が入力した文字列はすべてエスケープして表示。
壊れたデータ読めない端末内データは退避してから通知。クラウド側の不正データは画面に出さないが、書き換えもしない。
タップ領域・文字主要ボタンは高さ40px以上。入力欄は16px以上（iOS の自動ズーム防止）。セット入力行は 320px 幅でも1行。

12. 見た目の設計

  • 基準は承認済みモック mock/mock.html。上段の赤い面にカレンダーと負荷量、下段に操作と記録という構成です。
  • 色は :root のトークン（--hero-bg、--accent、--ink など）で管理し、黒テーマは :root[data-skin="black"] でトークンだけを差し替えます。部品側に色を直書きしません。
  • 数字と英字は Oswald、本文は Noto Sans JP。数字は等幅数字（tabular-nums）。
  • ブレークポイント：〜359px／〜374px／〜413px（スマホの詰め方3段階）、960px〜（PC）。幅が小数になる端末があるため境界は .98px で指定しています。
判断保留赤テーマの一部（カレンダーの記録あり日 3.1:1 など）は、元にしたアプリの配色を踏襲しておりコントラストが低めです。実機での見え方を確認してから調整します。

13. テスト設計

種類内容
自動テストtests/test.html をブラウザで開くと実行（v1.2.0 時点で 160 件、全 PASS）。対象は計算、日付、URL 解析、store の保存・削除・退避、Firestore を模した部品を使った同期（遅れて届くスナップショット、未 ready 時の保存拒否、切替中の保存不可、移行、再接続、ログイン連打など）、設定と Service Worker とルールの整合、記録写真の文字組みと縮小計算。
独立した手動テスト開発とは別の担当が、スマホ幅（320〜430px）と PC 幅で実際に操作。既知のデータを入れて集計値を手計算と照合し、異常入力・戻る操作・両テーマ・誤タップを確認。指摘は修正後に再確認。
実機・実ログインでの確認（利用者）開発側は Google にログインできないため、ログイン後の同期、移行、オフライン記録、iPhone のホーム画面アプリからのログイン、音、ノッチ周りは利用者が確認する（手順書 5章）。

14. 既知の制約と今後の候補

  • 同期の単位は「1日＝1ドキュメント」。2台で同じ日を同時に編集すると、後から保存した方が残ります。
  • 初めてログインした端末は、最初の読み込みが終わるまで（オンラインになるまで）入力できません。安全側の仕様です。
  • iPhone でアプリが裏に回った時や画面ロック中は、タイマーの音は鳴りません（復帰時に通知）。
  • 「元に戻す」は直前の1件だけです。
  • 更新の反映は「開いた次の起動から」です（Service Worker の方式上）。
  • 今後の候補：自己ベストのバッジ、CSV／JSON 書き出し、ホーム画面アプリ向けの別ログイン方式、赤テーマのコントラスト調整、週別バーへの数値表示。
