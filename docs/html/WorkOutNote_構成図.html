1. ひとことで言うと

アプリ本体は「Webページ」App Store は使いません。GitHub Pages という無料の置き場からアプリを読み込み、iPhone ではホーム画面に追加してアプリのように使います（この方式を PWA と呼びます）。
記録は「クラウドの保管庫」へGoogle の Firebase（Firestore）に保存します。iPhone で入れた記録が PC にもすぐ出ます。
電波がなくても記録できる端末の中に「控え」を持ち、つながった時に自動で送ります。ジムの電波が弱くても大丈夫です。
費用は 0 円・広告なし使っているサービスはすべて無料枠の範囲内です。見られるのはログインした本人だけです。

2. 全体構成図（登場人物と役割）

左が手元の端末、右がインターネット上のサービスです。端末とサービスの間のやり取りは ①②③ の3種類だけです。

3. 構成要素の一覧

要素たとえると役割提供元・費用
WorkOut Note（PWA）アプリそのものカレンダー、セット入力、集計、グラフ、タイマーなど全画面。HTML / CSS / JavaScript だけで作られ、端末のブラウザの中で動く。自作・0円
GitHub Pagesアプリの配布棚アプリのファイル一式を公開URLで配る。記録データは置かない。GitHub・無料
GitHub リポジトリ / Actions原本の保管庫と自動配送係プログラムの原本と変更履歴を保管。変更を受け取ると自動で GitHub Pages に反映する。GitHub・無料
Firebase Authentication受付の本人確認Google アカウントでログインさせ、利用者ごとの ID（uid）を発行する。Google・無料枠
Cloud Firestore記録の金庫日々の記録・体組成・種目一覧・設定を保存。変更を他の端末へ即時に通知。オフライン用の控えも管理。Google・無料枠（1日あたり読み取り5万回・書き込み2万回まで。個人利用では十分）
Service Worker端末内の倉庫番アプリのファイルを端末に控えておき、電波がなくても起動できるようにする。ブラウザの標準機能
端末内の保存領域手元のメモ帳未ログイン時の記録（localStorage）、ログイン中の控えと送信待ち（IndexedDB）、テーマの選択。ブラウザの標準機能

4. 記録が同期される流れ

入力した瞬間にまず端末の中へ保存するので、画面はすぐ反応します。クラウドへの送信はその後ろで自動的に行われます。

6. アプリ内部の構成（プログラムの層）

プログラムは上から「画面」→「司令塔」→「保存の窓口」→「保存先」の順に積み重なっています。画面は保存先がどこかを知らず、窓口（store.js）に頼むだけです。だから保存先を端末内とクラウドで入れ替えても、画面側は変える必要がありません。

7. データの形（保管庫の中身）

Firestore の中は「フォルダと書類」のような入れ子になっています。いちばん外側が利用者ごとの箱（users/{uid}）で、その中に4種類の書類が入ります。

8. セキュリティ（誰が読めるか）

補足：公開されているもの・いないもの公開＝アプリのプログラム一式（GitHub の公開リポジトリ）と接続先情報。非公開＝トレーニング記録、体組成、メールアドレス、パスワード（そもそもアプリは受け取りません）。

10. 用語集

用語意味
PWAWeb ページをアプリのように使える仕組み。ホーム画面にアイコンを置け、全画面で開き、電波がなくても起動できる。
GitHub PagesGitHub が提供する、ファイルをそのまま Web 公開する無料サービス。
GitHub ActionsGitHub 上で決まった作業を自動実行する仕組み。ここでは公開作業を自動化している。
FirebaseGoogle のアプリ向けクラウドサービス群。このアプリはログイン（Authentication）とデータベース（Firestore）を使う。
uidFirebase がログインした人ごとに発行する ID。データの持ち主を区別する。
Service Workerブラウザの裏で動く小さなプログラム。ファイルの控え（キャッシュ）を管理する。
localStorage / IndexedDBブラウザが端末内に持つ保存領域。前者は小さなメモ帳、後者は本格的な保管箱。
SDKサービスを使うための公式の部品一式。ここでは Firebase JS SDK 12.19.0。
推定1RM1回だけ挙げられる最大重量の推定値。このアプリでは 重量 ×（1 + 回数 ÷ 40）。
